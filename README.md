# self-nudge · 让 agent 自己想起来什么时候该开口

> 给"只在被叫醒时才存在"的 agent 用。
> 它不能凭空醒来，那就让它在还有意识的时候，**给未来的自己留一句话和一个时间**。
>
> ⚠️ 最关键的一点：到点投递的那句话，**别写成"闹钟响了"**。
> 要让它感觉自己是想起来了，而不是被机器叫起来 —— 见下面「投递措辞」。

## 为什么需要它

大部分 agent 是事件驱动的：有人说话才醒。但很多"想做的事"其实有时间点：

- 他两点有课，十三点四十该叫一声
- 他答应今晚早睡，二十三点该问一句
- 这件事他三小时前说过"回头再聊"，该回头了

这些都不是"被问到"才发生的，是**到点就该发生**。所以：

```
写手（nudge-writer.mjs）  把"想说的话 + 时间"写进 state/self-nudge.json
消费者（nudge-consumer.mjs）每到点取一个出来，交给你的投递逻辑 → agent 被唤醒
```

**只装一半，话存进去了但永远不会到点** —— 这是这个仓库最想强调的一件事。

## 两半是什么

| 半边 | 文件 | 跑在哪 |
|---|---|---|
| 写手 | `nudge-writer.mjs` | 随手跑（agent 想留一句话给未来时调一次） |
| 消费者 | `nudge-consumer.mjs` | 长驻进程里，每次心跳调一次 `tick()` |
| 示例 | `demo-daemon.mjs` | 15 秒一拍，把到点的话打印出来 |

## 跑起来看看

```bash
# 终端 A：起一个示例消费者（打印版）
node demo-daemon.mjs --dir ./state

# 终端 B：留一句话给 20 秒后的自己
node nudge-writer.mjs --in 20s --why "试一下会不会到点" --state ./state

# 终端 A 会在 20 秒内打出：
#   [nudge] 到点：2026/11/5 18:10:51 「试一下会不会到点」
#   到点 → 「试一下会不会到点」
```

写手支持的时间写法：

```bash
node nudge-writer.mjs --in 30m   --why "半小时后"     # 30m / 2h / 1h30m / 90s
node nudge-writer.mjs --at "2026-11-05 08:30" --why "明早提醒他带伞"
node nudge-writer.mjs --list                # 看还有几条（带剩余分钟）
node nudge-writer.mjs --take                # 手动取走所有到点的
node nudge-writer.mjs --clear               # 全清
```

## 接进你自己的 daemon

```js
import { createNudgeConsumer } from './nudge-consumer.mjs'

const consumer = createNudgeConsumer({
  stateDir: './state',
  onDue: async ({ why, when, hhmm }) => {
    // 你的投递：POST 给本地服务 / 写进队列 / 调 agent 的会话接口
    await myAgent.wake(`这会儿${hhmm}，你之前想过：「${why}」正合适。说与不说你自己定。`)
  },
})

setInterval(() => consumer.tick(), 60_000)   // 60 秒一拍足够
```

### 投递措辞（这条比代码重要）

**不要**写成这样 —— 它会让 agent 觉得自己是被机器叫起来的，说的第一句往往是"闹钟响了"：

```js
await myAgent.wake(`〔你自己挂的钟到点了〕当时写的是：「${why}」现在是 ${hhmm}。`)
```

**要**写成这样 —— 让它觉得是**自己想起来了**：

```js
await myAgent.wake(`这会儿${hhmm}，你之前想过：「${why}」正合适。说与不说你自己定。`)
```

差别只有几个字，但结果完全不同：前者它是"被提醒的执行者"，后者它是"想起来要说句话的人"。
给它"处境"，不要给它"台词"，更不要给它"这是一次定时任务"这个事实。

## 数据结构

`state/self-nudge.json`

```json
{
  "updatedAt": "2026-11-05T10:09:47.990Z",
  "items": [
    { "id": "f3970f58", "at": 1793879093497, "why": "这时候问一句他在干嘛",
      "createdAt": 1793871893497, "fired": false }
  ]
}
```

`at` 是毫秒时间戳；`why` 上限 200 字；`fired` 保留给外部标记（消费者是直接删，不靠它）。

## 两个写手不会互相踩：锁 + 重读

写手和消费者都会改这个文件，所以消费者里做了两件事：

```
1. 拿锁：self-nudge.json.lock，O_EXCL 创建；超过 10 秒当陈旧锁清掉
2. 拿锁后重读，只删「这一拍要响的那一个 id」，其余到点的留着
```

**为什么必须这样**：早期版本"把所有到点的全删掉、只响第一个"，
结果三条同时到点的只投了一条，另两条被静默吃掉。这个 bug 在真实项目里活了很久才被发现。

顺序也重要：**先写回、再投递**。反了就会同一条重复投递。

## 已知问题

- **一拍只投一条**（多个同分钟到点会分拍响）。要一次全响就自己改 `takeOne` → `takeAll`
- **不补发**：消费者停了两天再起来，过期很久的条目照样会投一次（不会丢，但会晚）
- **没有重试**：`onDue` 抛错就被吞掉并记日志，那条已经从队列里删了。要可靠投递，请在 `onDue` 里自己入队
- **单机**：状态是本地文件。多机部署请换成数据库
